# SEO content

The Content editor has separate SEO scopes for Home, Services, Portfolio, Shop, About, Contact, Reviews, the generic product page, 404, order confirmation and Stripe onboarding confirmation. Save and preview a private draft, then publish it using the existing conflict checks and history. Only metadata already present in each template is editable. Confirmation pages retain their protected `noindex,nofollow`; canonical URLs and page structure are not editable. Admin, sauna and other paths are not SEO scopes.

The product scope changes generic fallback metadata. For product URLs with an ID, the edge function also requests the existing public product API and uses a valid public product's name and subtitle in server-delivered metadata. If the ID or product is invalid, missing, unavailable or the API fails, the generic fallback remains; a missing subtitle leaves the generic description. The API itself may serve its static seed data during storage failures. When product data loads in the browser, the existing client script still sets the product-specific title and available subtitle.

An edge function reads the downstream HTML and obtains only the published SEO scope from a same-site serverless function. It requests an uncompressed downstream response and escapes text before replacing existing metadata. It also recognizes the site's 404 template on unknown routes and preserves the 404 status; unrelated errors pass through. If no scope is published, storage is unavailable, or the template does not match, generic metadata falls back to the original static values. Responses that remain encoded, range requests, redirects, non-HTML responses and non-GET requests are not rewritten. Dynamic HTML responses use `no-store`; a storage timeout can temporarily show the original static metadata. The 404 handling requires the edge function to inspect downstream responses for all GET paths, which can add overhead; product URLs additionally require a public API lookup.

Before release, verify edge-function discovery and packaging, same-site function requests, Blobs credentials and strong reads, conditional requests, security headers, redirects and actual crawler-visible output in the intended Netlify environment. Netlify Blobs stores are site-wide, so avoid publishing test edits into the production site's store. There has been no deployed verification; edge execution, internal function latency, platform caching and encoded-response behavior remain deployment risks. Roll back by removing the edge function declaration/build output; original static pages remain intact.
